## 深查：为什么 LLM 一次都不调 graph-query（用户点名"不顺利要深查"）

逐项排查清单的结论：

1. **SKILL.md 措辞不是主因**——可选步骤写得清楚（"仅当任务问历史案例/法条依据时"），且 hist1/hist2 的任务明确问了。
2. **真正根因：子智能体的任务文本里没有这个问题。** trace 显示③规则推理收到的 task 只包含研判指令——历史案例的问题在**主智能体层**被消化了（hist1 的回答"历史案例库无记录"来自主智能体自己 `search_files`/知识检索或上下文，不是③的回答）。子智能体按 SKILL.md"仅当任务问"的判断完全正确：它的任务没问，就不查。
3. **次因：工具序列极简。** ③的 trace 是 `skill_view(rule-reasoning-core) → terminal(run_rule_reasoning) → 结束`——LLM 严格遵循"就这三步"的反瞎逛纪律（这正是之前训练出的好行为），第 4 步的可选提示没有触发。
4. 输出 JSON 长度/格式无问题（Task4 已实测 <500 字符单行）。

结论：**不是 ctgu-vlm 不听话，是架构上问不到**——历史类问题到不了③的任务文本里，graph-query 在③侧永远等不到触发条件。

## 处置（按计划 Step 5 的"不达标处置"）

- **阶段 C 的 SKILL.md 可选步骤改动：保留但不追加强制化**（0 调用不是 bug 而是架构分层使然；强制化=让③查图反而违背"反瞎逛"纪律）
- graph-query 技能与脚本**保留**（无害，Task4 已验证；主智能体侧未来可发现使用）
- **价值兑现路径已由阶段 A+B 承接**：脚本内图查询 10/10 生效（used_graph=true、法条 §39/§83 进入研判结果、案例库含写回案例）——这正是用户要的"减少 grep 耗时耗算力"
- 若未来要让 LLM 主动查图：改主智能体编排技能（orchestrator-core 加"历史类问题调③时把问题透传"）——记录为后续可选项，不阻塞子项目3
